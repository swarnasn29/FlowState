Why session-replay tools cannot do this

Three friction types are visible in the UI. The fourth is the expensive one.

Friction What the user experiences Seen by UI-only tools Needs chain data
stallA spinner that never resolves YesNo
error_loopThe approval or slippage trap, repeatedly YesNo
rage_clickThe button looks dead, so they hammer it YesNo
silent_failure It worked. The UI never said so. No — invisible Yes

FlowState reads the interface and the chain for the same moment. The only evidence of a silent failure is the disagreement between them, which is why this belongs on a chain-native network rather than in a session-replay product.

The subnet

A market for finding the broken step

dApps

Send telemetry

UI interactions plus wallet and chain events, per session.

Validator

Asks, and marks

Generates sessions with a known answer. Relays real ones with none.

Miners

Locate the friction

Return the step index, the kind, and a confidence.

Chain

Pays the accurate

Accuracy becomes weight. Weight becomes emissions.

Every request is signed with the caller's hotkey and checked against the metagraph before a miner spends any CPU. Bittensor v11 removed the axon, dendrite and Synapse stack, so the transport is our own signed HTTP, written from the migration notes.

The hard part was never detection

Real telemetry has no answer key

A miner replies "friction at checkout, confidence 0.8." Nobody knows whether it is right. Three things break at once.

A lazy miner cannot be caught

One answering "step 3" every time looks identical to one doing real work.

Honest validators disagree

Two of them grade differently, diverge, and Bittensor's consensus penalises both.

Quality scoring gets gamed

Score the report and miners optimise the proxy: longer text, more confident language.

Scored stream

The validator writes the question

  • Synthetic session, friction injected at a known index
  • The answer never leaves the validator
  • This alone sets weights, because it is the only thing verifiable

Organic stream

A real dApp sends a real session

  • No known answer, because nobody knows it
  • The report goes back to the dApp
  • Never scored. This is the product, not the test

The two are byte-identical on the wire. A miner that could tell them apart would work hard only when marked, so the distinction lives entirely on the validator's side. Passing the exam is how a miner earns the right to serve the traffic.

The 0.32 gap between calibrated and cold is the result that matters. Identical code; the only difference is traffic it has learned from. Every cheat scores below an untrained miner, because no fixed threshold survives a step that is legitimately slow — a healthy tx_pending runs to 45 seconds under congestion, longer than many injected stalls.

A session carries zero, one or two friction points — 30% of them none at all — so a miner returns a set, possibly empty, and has to decide whether anything is wrong before deciding where. Answering a clean session with silence scores 1.00; a confident false positive scores 0.02. That is also why "claim nothing, ever" scores 0.280: it is simply the fraction of sessions that are genuinely clean.

Scoring is four named criteria rather than one boolean, and the validator prints them on every run, because a rule miners cannot read is a rule they reverse-engineer: localisation 0.70 (F1 over the reported step indices), kind 0.20, calibration 0.10 (1 − Brier over its own confidences), and latency as a pass/fail gate. Four guesses at two frictions scores 0.64 — below honestly finding one of them at 0.76 — so flooding the response cannot pay.

What this does not claim

The limits, and the things that went wrong

Deliberately not built

  • Consensus scoring for organic traffic. Comparing miners against each other risks rewarding conformity over correctness.
  • A real dApp feed. Organic sessions are currently fabricated with their answers discarded.
  • A second flow. Everything assumes a token swap.
  • Pruning. A useless miner earns nothing but keeps its uid.

Found by testing my own work

  • A label leak. The injected friction tagged itself, so one line of code scored 75% with perfect precision.
  • Weights paid on luck. A per-challenge average with a five-sample memory split emissions 100/0. It reached the chain before it was caught.
  • A silently discarded endpoint. The chain accepts a loopback address and stores zero, leaving a miner invisible while it looks healthy.

Every figure on this page is produced by a script in the repository, on every run — including the lazy-strategy baselines, so a future leak shows up instead of quietly inflating the score.
